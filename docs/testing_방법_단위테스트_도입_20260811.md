# platform 단위 테스트 방법

`platform`은 Google Test 기반의 자체 검증용 테스트 스위트를 갖는다.
이 문서는 빌드·실행 방법과, 새 기능을 추가할 때 테스트를 어디에 어떻게 작성해야 하는지를 설명한다.

관련 문서: [`docs/brainstorming/단위테스트_도입_20260811_2033.md`](brainstorming/단위테스트_도입_20260811_2033.md), [`docs/strategy/단위테스트_도입_20260811_2210.md`](strategy/단위테스트_도입_20260811_2210.md), [`docs/dependency/googletest_20260811.md`](dependency/googletest_20260811.md)

## 전제

- 테스트는 platform 레포 **자체 검증용**이다. platform을 서브모듈로 가져가는 상위 프로젝트(예: `World-of-Tank-imitation-Refactoring`)는 이 테스트 빌드를 켤 의무가 없다 — "platform은 자체적으로 검증됨"이 기준이며, platform 동작이 의심되면 검증·수정은 platform 레포 안에서 이루어진다.
- platform은 GitHub 저장소명과 동일하게 폴더명이 `platform`인 상태로 체크아웃되어 있어야 한다(기존 소스가 전부 `#include "platform/xxx/Yyy.h"` 형태로 스스로를 참조하는 레포 전체 관례를 따르기 위함).

## 빌드 방법

```
# platform 폴더에서 실행 (platform 폴더의 부모 디렉터리가 include root가 된다)
cmake -S . -B build -DPLATFORM_BUILD_TESTS=ON
cmake --build build --config Debug --target platform_tests
```

- `PLATFORM_BUILD_TESTS`는 기본값 `OFF`다. 이 옵션을 켜지 않으면 `platform_lib`만 빌드되고 GoogleTest는 아예 받아오지 않는다.
- 최초 빌드 시 GoogleTest(1.17.0), nlohmann_json, tinyobjloader, ufbx, cgltf를 `FetchContent`로 받아오므로 네트워크가 필요하다.

## 실행 방법

두 가지 방법 중 편한 쪽을 쓴다.

```
# 1) CTest로 전체 실행
cd build
ctest -C Debug

# 2) 실행 파일 직접 실행 (특정 케이스만 필터링하고 싶을 때)
build/tests/Debug/platform_tests.exe --gtest_filter=Matrix4x4Test.*
```

## 디렉토리 구조 규칙

`platform/tests/`는 소스 폴더 구조를 그대로 미러링한다.

```
platform/
  math/Matrix4x4.h, Matrix4x4.cpp, ...
  tests/
    math/Matrix4x4Test.cpp, Vec2Test.cpp, ...
    geometry/...
    collision/{bvh,gjk_epa,...}/...
    entity_component/...
    logging/...
    model_import/...
    persistence/...
    serialization/...
    engine/...
    Win32WindowTest.cpp      (Win32Window.h/.cpp가 루트에 있으므로 테스트도 루트)
    fixtures/model_import/   (모델 임포터 테스트용 샘플 파일)
```

- 테스트 파일명은 `<클래스명>Test.cpp`.
- 테스트 케이스 이름은 `TEST(<클래스명>Test, <검증하는 동작을 설명하는 이름>)` 형태로 짓는다.

## 새 기능 추가 시 테스트 작성 규칙

1. 새 클래스/모듈을 `platform/<module>/`에 추가하면, 같은 상대 경로의 `platform/tests/<module>/`에 대응하는 `<클래스명>Test.cpp`를 함께 추가한다.
2. `platform/tests/CMakeLists.txt`의 `add_executable(platform_tests ...)` 목록에 새 테스트 파일을 등록한다.
3. **목(mock) 설계 수준에서 멈추지 않고, 실제 동작을 자동화 검증하는 테스트까지 작성한다** — 이번 사이클 결정과 동일한 기준을 유지한다(브레인스토밍 참고). 격리가 필요한 경우 아래 패턴을 따른다.
   - 파일 I/O가 필요한 클래스(`model_import/`, `serialization/`, `logging/`의 파일 싱크 등): 임시 파일/디렉토리 픽스처를 테스트 안에서 만들고 `TearDown()`에서 정리한다. 고정 샘플 파일이 필요하면 `platform/tests/fixtures/`에 추가한다.
   - OS 핸들이 필요한 클래스(`Win32Window`, `model_import/Win32FileWatcher`): message-only window 또는 임시 디렉토리처럼 실제 OS 자원을 사용하되 화면에 보이지 않거나 부작용이 없는 방식으로 실제 API 호출을 검증한다.
   - 외부에 의존하는 협력 객체가 필요한 경우(`persistence/SaveLoadManager`의 `ISaveable`, `IDataStore` 등): platform 범위 안의 최소 테스트 더블(Fake)을 만든다 — 상위 프로젝트의 구체 클래스를 참조하지 않는다(platform은 상위 프로젝트를 몰라야 한다).
4. 성능·메모리 등 단위 테스트만으로 다루기 어려운 검증이 필요해지면, 이 문서와는 별도로 `platform/docs/`에 새 `.md`를 추가해 누적한다(이번 사이클 범위 밖).

## 신규 외부 의존성 추가 시

새 테스트 프레임워크가 아닌 새 "제품" 의존성(예: 새 모델 포맷 파서)이 필요해지면, 먼저 `agent_harness`의 Dependency Evaluation 절차(`docs/dependency/library-name_YYYYMMDD.md`)를 거친다.

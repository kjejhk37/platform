# platform 릴리스 파이프라인 및 로드맵

`platform → graphics → World-of-Tank-imitation-Refactoring(WOT)` 3개 저장소를 git 소스 공유 방식에서 DLL 기반 릴리스 소비 방식으로 전환하기 위한 전체 파이프라인과, 그 안에서 platform 저장소가 맡는 역할을 정리한 문서.
같은 내용이 형제 저장소에도 각자의 관점으로 기록되어 있다 — `graphics/docs/architecture/릴리스_파이프라인_전략.md`, `World-of-Tank-imitation-Refactoring/docs/architecture/릴리스_파이프라인_전략.md`.
`platform_graphics_projects.md`, `docs/algorithm/`과 동일하게 사이클 종료 후에도 archive하지 않고 이 위치에 영구 보관하며, 파이프라인 관련 논의가 진행될 때마다 갱신한다.
최초 작성: 2026-08-13.

---

## 결론

- 지금은 세 저장소 모두 "릴리스 버전"이 없는 상태다 — graphics/WOT은 platform을 git submodule 소스로 직접 참조한다.
- 핵심 문제는 개발 편의성이 아니라 **검증**이다: platform/graphics가 독립적으로 검증·릴리스되지 않은 채로 WOT에 소스로 얹히기 때문에, WOT에서 문제가 생겨도 platform/graphics/WOT 중 어디가 원인인지 구분할 수 없다.
- 해결 방향은 platform을 DLL(+헤더+lib+pdb)로 버전 태그를 붙여 릴리스하고, graphics는 그 특정 버전을 고정해서 소비하고 자신도 릴리스하며, WOT은 두 릴리스 버전을 고정해서 소비하는 구조다.
- 최초 릴리스가 아예 없는 지금은 1회성 "부트스트랩 사이클"로 릴리스 인프라(CI 게이트, semver 태깅, nightly/stable 채널)를 구축하는 게 목표이고, 이후에는 훨씬 가벼운 정상 개발 사이클로 넘어간다.

## 배경 — 지금 방식의 문제

- graphics/WOT이 platform 소스를 git submodule로 직접 참조하고 있어, platform 코드가 바뀌면 검증 없이 상위로 그대로 흘러들어간다.
- platform은 자체 Google Test 스위트(10개 영역, 247케이스)를 갖고 있지만, 이게 "릴리스 가능 상태"를 보증하는 게이트로 쓰이고 있지는 않다 — 테스트가 있다는 것과 "이 커밋은 릴리스해도 되는 버전이다"라고 태깅하는 것은 다른 일이다.
- 결과적으로 WOT에서 회귀가 발생해도 "platform 몇 번 커밋부터 문제였는지" 재현·이분탐색(bisect)하기 어렵다.

## 계층 컨셉 (참고: `platform_graphics_projects.md`)

platform이 지켜야 할 경계는 WOT 저장소의 `docs/architecture/platform_graphics_projects.md`에 이미 확정되어 있고, 이 문서는 그 경계를 바꾸지 않는다 — 그 경계를 지킨 상태로 어떻게 "릴리스 가능한 단위"로 배포할지만 다룬다.

- **platform**: 검증된, 완전히 추상화된 최소 단위 기능/데이터 라이브러리. graphics/WOT 어느 쪽도 몰라야 한다.
- **graphics**: platform을 사용해 특정 그래픽스 API를 캡슐화하는 렌더링 계층. WOT을 몰라야 한다.
- **WOT**: platform과 graphics를 모두 사용해 실제 게임을 구현하는 최하위 계층.

## 전체 파이프라인 구조

```
[platform] --DLL(+header+lib+pdb), semver 태그--> [graphics] --DLL(+header+lib+pdb), semver 태그--> [WOT]
   자체 CI: merge마다 테스트 통과 필수                  platform 특정 버전 고정 + 자체 테스트         platform+graphics 특정 버전 고정, 소스로 남음(최종 제품)
```

platform은 이 체인의 최하단이라 릴리스 파이프라인을 가장 먼저 갖춰야 한다 — platform이 검증 안 되면 그 위에 뭘 쌓아도 의미가 없다.
platform은 계속 소스 레포로 유지하되, "릴리스 가능한 커밋"에는 DLL 아티팩트(런타임 `.dll` + 링크용 `.lib` + 디버깅용 `.pdb` + 공개 헤더)를 붙여서 배포한다.

## 릴리스 채널: nightly(개발용) vs stable(정식)

- **nightly/prerelease**: platform main에 merge될 때마다 자체 테스트(`platform_tests`, `PLATFORM_BUILD_TESTS=ON`)를 통과하면 자동으로 prerelease 버전(예: `1.4.0-nightly.234`)을 발행한다. graphics는 개발 중 이 채널을 계속 추적한다.
- **stable**: 정식 기능이 안정화되면 semver 태그(`vMAJOR.MINOR.PATCH`, `agent_harness`의 `git_workflow.md` 태그 규칙과 동일)로 확정 릴리스한다. graphics/WOT은 출시가 임박하면 이 stable 버전에 고정(pin)한다.
- 버전 증가 규칙: MAJOR(하위 호환 깨짐) / MINOR(하위 호환 유지되는 기능 추가) / PATCH(버그 수정). Conventional Commits 스타일 커밋 메시지(`feat:`, `fix:`, `BREAKING CHANGE:`)로 자동 판단하는 걸 목표로 하되, 자동화 도입 전까지는 수동으로 규칙을 지켜 태깅한다.

## ABI/배포 시 유의할 점

- Windows DLL은 런타임용 `.dll`과 링크용 `.lib`가 한 쌍이며, 소비자(graphics)에게 둘 다 배포해야 한다. 디버깅을 위해 `.pdb`도 함께 배포한다.
- MSVC 버전, 런타임 링크 옵션(`/MD` vs `/MT`)이 graphics와 어긋나면 ABI 문제가 생긴다 — 이 옵션을 platform 릴리스 규격으로 문서화해서 고정한다.
- 공개 헤더 경계에서 STL 컨테이너를 그대로 넘기는 API는 피하고, 필요하면 PIMPL 패턴으로 구현 세부사항을 감춘다. 신규 공개 API를 추가할 때 이 기준을 함께 검토한다.

## 기능 구분 프로세스 — 추상화된 기능 vs 프로젝트 특화 기능

- WOT에서 새 기능이 필요할 때, 그 기능이 "누구든 재사용 가능한 일반 원칙"이면 platform 소속 후보다 — `platform_graphics_projects.md`의 핵심 질문("이 타입/기능의 모양을 누가 결정하는가")을 그대로 적용한다.
- platform은 해당 기능을 추상 기반(제네릭 메커니즘/인터페이스)으로 제공하고, WOT은 이를 상속·구현해 프로젝트 특화 동작을 만든다 — platform 자체에 WOT 전용 콘텐츠가 섞이지 않도록 한다.
- 이 경계 판단은 platform 세션 혼자 정하지 않는다. WOT/graphics 세션과 문서(브레인스토밍/전략 문서 또는 이 architecture 문서)를 주고받으며 토의하고, 필요하면 ChatGPT 등 외부 의견도 참고해 platform 컨셉이 흐트러지지 않는지 확인한 뒤에만 병합·버전을 올린다.

## 로드맵

1. **부트스트랩(현재 진행)**: platform CI에 자체 테스트 게이트 + semver 태깅 + nightly/stable 아티팩트 발행 파이프라인을 구축한다. 최초 stable 릴리스를 만든다.
2. **정상 사이클 전환**: 이후 기능 요청은 "① 기획 → ② platform 내부 개발로 처리할지 검토 → ③ 개발·반복" 흐름을 따르고, platform 쪽 작업은 merge마다 자동으로 nightly 패키지가 나오는 파이프라인 위에서 진행한다.
3. 이 문서는 파이프라인이 바뀔 때마다(예: 패키지 매니저 도입, CI 도구 확정 등) 갱신한다.

# 단위테스트_도입 — Brainstorming

## Details

`platform`은 상위 프로젝트 CMake 빌드에 편입되는 서브모듈 라이브러리로, 단독 빌드 스크립트가 없다.
현재 `collision/`, `engine/`, `entity_component/`, `geometry/`, `logging/`, `math/`, `model_import/`, `persistence/`, `serialization/`, `Win32Window`까지 10개 영역에 소스는 있지만 테스트 코드와 테스트 빌드 체계가 전혀 없다.
`agent_harness/CLAUDE.md`의 Core Development Principles가 "모든 기능에 단위 테스트를 작성한다"를 명시하고 있어, 이번 작업은 (1) 테스트 빌드 인프라를 처음 도입하는 것과 (2) 기존 코드에 소급 적용하는 것 두 가지를 동시에 다룬다.

사용자가 Task Document를 아래와 같이 직접 확정했다(2026-08-11).

- 목표: platform submodule에 대한 기능 검토 및 단위 테스트 스크립트 작성.
- Claude 요구 사항: (1) 현재 platform 내 기능 검토 및 각 기능에 대한 단위 테스트 스크립트 작성, (2) 작성된 단위 테스트를 기반으로 하는 단위 테스트 방법을 .md로 작성.

이 확정본을 반영하면 기존 안과 비교해 두 가지가 달라진다.

- **"각 기능에 대한"**이라는 표현은 특정 우선순위 모듈만이 아니라 10개 영역 전체를 대상으로 함을 시사한다 (아래 범위 논의는 이 전제로 갱신).
- 산출물이 테스트 코드뿐 아니라, 작성된 테스트를 어떻게 실행/활용하는지 설명하는 **테스트 방법 문서(.md)** 까지 포함된다(확정). `platform/README.md`에 섹션을 추가하는 대신, `platform/docs/` 안에 별도 `.md` 문서 하나를 추가하는 방식으로 확정한다 — 정확한 파일명은 Strategy 단계에서 정한다.

검토한 항목은 다음과 같다.

- **테스트 프레임워크(확정)**: Google Test를 `FetchContent`로 받아오는 방식으로 확정한다. `World-of-Tank-imitation-Refactoring/docs/dependency/googletest_20260715.md`에서 이미 평가·검증을 마친 결정(버전 1.17.0, BSD-3-Clause, MSVC 19.37/Ninja 빌드 확인)과 통일한다.
- **wrapper 정책(WOT 선례 준용)**: `agent_harness`의 "외부 라이브러리는 내부 wrapper 클래스로 감싼다" 원칙은 GoogleTest에는 클래스 래퍼가 아니라 **빌드 타겟 경계**로 적용한다 — WOT 프로젝트에서 이미 이 예외를 확정한 선례를 그대로 따른다. platform 라이브러리 타겟 자체는 gtest에 의존하지 않고, 신규 테스트 실행 타겟에만 `gtest`/`gtest_main`을 링크한다.
- **CMake 통합 방식(확정)**: `platform/tests/CMakeLists.txt` + 옵션 플래그(`PLATFORM_BUILD_TESTS`)로 구성하되, 이 옵션은 **platform 레포 자체 검증용**이며 상위(소비) 프로젝트가 필수로 연동할 필요는 없다. platform을 서브모듈로 가져가는 프로젝트는 이 테스트 빌드를 켤 의무가 없고, "platform은 자체적으로 검증됨"이 기준이다 — platform의 동작이 의심되면 검증·수정은 platform 레포 안에서 이루어진다.
- **디렉토리 구조**: 소스 폴더 구조를 그대로 미러링(`tests/math/`, `tests/geometry/` 등)하면 어떤 모듈이 테스트를 갖췄는지 한눈에 파악하기 쉽다.
- **모듈별 테스트 난이도 편차**: `math/`, `geometry/`, `collision/`의 순수 알고리즘 계열은 입출력이 결정적이라 테스트 작성이 쉽다. 반면 `model_import/`(파일 I/O, 외부 파서 래퍼), `Win32Window`(OS 핸들 의존), `logging/`의 파일 싱크 계열은 격리하려면 파일 시스템 모킹이나 인터페이스 목(mock) 객체가 추가로 필요해 난이도와 작업량이 크다.
- **범위 크기 및 깊이(확정)**: 10개 영역 전체를 대상으로 하되, 깊이도 가능한 한 균일하게 맞춘다 — "실제로 작동하는지"를 검증하는 것이 핵심이므로, `model_import`/`Win32Window`처럼 I/O·OS 의존적인 영역도 목(mock) 인터페이스 설계 수준에서 멈추지 않고 실제 동작을 자동화 검증하는 테스트까지 작성한다. 다만 격리를 위한 테스트 더블(예: `model_import`는 임시 파일 기반 픽스처, `Win32Window`는 message-only window 또는 더미 HWND)은 필요에 따라 구성한다.
- **기능 검토(1단계) 산출물(확정)**: 별도의 검토 문서를 남기지 않고, 단위 테스트 코드 자체를 기능 검토의 산출물로 삼는다. 성능·메모리 등 단위 테스트만으로 다루기 어려운 항목이 필요해지면 그때 별도 `.md`를 추가로 누적하는 방식으로 확장한다 — 지금 단계의 기준은 단위 테스트다.

## Trade-offs

- **Google Test(FetchContent) 채택(확정)**
  - 장점: 업계 표준, matcher/assert 매크로가 풍부, WOT 프로젝트와 도구 체계가 통일되어 두 프로젝트 간 테스트 작성 관습이 갈리지 않는다.
  - 단점: 외부 의존성이 하나 늘고, 최초 빌드 시 다운로드/컴파일 시간이 추가된다. wrapper 원칙은 클래스 래퍼 대신 빌드 타겟 경계로 적용하기로 WOT 선례를 따라 확정했다(위 Details 참고).
- **전 모듈 균일 깊이 착수(확정)**
  - 장점: "실제로 작동하는지"가 목표이므로, 목(mock) 설계 수준에서 멈추지 않고 전 영역에서 동일한 신뢰 수준을 확보한다.
  - 단점: `model_import`/`Win32Window`처럼 테스트 더블 구성이 추가로 필요한 영역이 있어 전체 작업량과 Step 3 체크리스트 크기가 커진다 — Strategy 단계에서 모듈별 테스트 더블 설계를 구체화해야 한다.
